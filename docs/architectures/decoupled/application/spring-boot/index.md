# Spring Boot 아키텍처

본 문서는 Spring Boot 기반 백엔드 애플리케이션의 **품질 목표와 그것을 달성하는 전략, 그리고 규칙의 강제 수단**을 정의합니다.

특정 시스템 하나의 명세가 아니라 **여러 프로젝트에 적용하는 규범집**입니다. 프로젝트마다 달라지는 항목은 판단 기준만 제시하고 구체 구성은 각 프로젝트 저장소가 소유합니다.

앱을 어떻게 나누고 프론트엔드와 무엇을 주고받는지는 [애플리케이션 아키텍처](../index.md)가, 무엇이 어디에 배포되는지는 [시스템 아키텍처](../../system/index.md)가 소유합니다. 본 문서는 **그 경계 안쪽의 코드**만 다룹니다.

문서 체계는 [arc42](https://arc42.org/)를 따르되 **원본을 가진 절만 둡니다.** 다른 문서가 이미 원본인 절은 목차가 되어 두 벌이 되므로 두지 않습니다. 구성 요소 간 관계 시각화에는 [C4 Model](https://c4model.com/) 표기 규약을 적용했습니다.

## 1. 서론과 목표

### 본 문서의 역할

본 문서는 백엔드 코드의 배치와 의존 방향을 정의합니다. 업무 기능이나 요구사항은 다루지 않으며, 그 원본은 각 프로젝트의 요구사항정의서와 유스케이스 명세서입니다.

주된 독자는 **작성자 본인과 AI 코딩 에이전트**입니다. 에이전트가 규칙을 읽고 코드를 올바른 위치에 배치하는 것이 1차 목적이며, 사람이 읽는 것은 2차입니다.

### 품질 목표

| 순위 | 품질 목표 | 정의 및 선정 사유 |
| :---: | :--- | :--- |
| **1** | **구조의 부패 저항 (Rot Resistance)** | 규칙이 문서에만 있으면 반드시 무너집니다. Java 컴파일러는 패키지 경계를 강제하지 못하므로, 별도의 강제 장치가 없는 규칙은 규칙이 아니라 권고입니다. |
| **2** | **도메인의 독립성 (Domain Isolation)** | 도메인은 프레임워크도 화면 요구도 알지 못해야 합니다. 둘 중 하나라도 도메인을 끌어당기기 시작하면 업무 규칙이 그것들의 사정에 따라 바뀝니다. |
| **3** | **변경 유연성 (Maintainability)** | 화면 요구사항은 빈번하게 변경됩니다. 표시 항목 하나가 추가된다는 이유로 도메인 구조가 수정되지 않아야 합니다. |
| **4** | **운영 단순성 (Operational Simplicity)** | 소규모 팀에서는 운영 복잡도가 늘어난 만큼 기능 개발 시간이 줄어듭니다. 1~3과 충돌할 때 양보하는 쪽입니다. |

**상기 네 목표의 우선순위가 4절의 전략을 결정하는 기준입니다.** 단일 배포를 채택한 근거는 목표 4이고, 조회 경로를 도메인 저장소에서 떼어 낸 근거는 목표 2와 3입니다.

프론트엔드 표준의 서열(예측 가능성 > 자동 강제 > 변경 유연성)을 그대로 따르지 않습니다. **서열은 그 스택이 무엇을 가장 잃기 쉬운가로 정해집니다.** 프론트엔드가 배치의 일의성을 먼저 잃는다면, 백엔드는 도메인이 프레임워크와 화면에 침식되는 쪽을 먼저 잃습니다.

### 이해관계자별 관심사

| 이해관계자 | 주요 관심사항 |
| :--- | :--- |
| **AI 코딩 에이전트** | 코드 배치 판정 규칙, 컨텍스트 경계와 참조 허용 범위 |
| **백엔드 개발자** | 계층 책임, 조회와 명령의 경로 구분, 저장소 구현 방식 |
| **프론트엔드 개발자** | 계약 변경 절차와 오류 응답 형식 |
| **DBA** | 스키마 변경이 애플리케이션에 미치는 영향 범위 |

## 2. 제약 조건

4절의 전략과 각 결정의 전제가 되는 제약사항입니다.

### 기술 스택

본 표준은 프레임워크 중립이 아니며 Spring Boot와 jOOQ를 전제합니다. 중립적으로 기술하면 규칙이 "계층을 적절히 분리합니다" 수준으로 흐려져 판정 기준으로 기능하지 못하기 때문입니다.

| 항목 | 값 | 비고 |
| :--- | :--- | :--- |
| **프레임워크** | Spring Boot | |
| **언어** | Java | |
| **데이터 접근** | jOOQ | 생성 레코드와 도메인 엔티티가 애초에 분리됩니다 |
| **마이그레이션** | Flyway | 마이그레이션 파일이 스키마의 단일 원본입니다 |
| **데이터베이스** | PostgreSQL | |
| **정적 분석** | Spotless · Checkstyle · SpotBugs | 설정 파일이 곧 코딩 표준입니다 |
| **구조 검사** | ArchUnit | 빌드 게이트에 포함합니다 |

버전과 의존성의 원본은 `build.gradle`입니다. 본 문서에 버전 목록을 중복 기재하지 않습니다.

**jOOQ를 전제로 두는 것이 목표 2와 직접 맞물립니다.** ORM은 엔티티가 곧 영속 객체라 도메인이 프레임워크 어노테이션을 달게 되지만, jOOQ는 생성 레코드와 도메인 엔티티가 처음부터 별개이므로 "도메인은 프레임워크를 모른다"가 타협 없이 성립합니다. 선택의 근거와 감수 사항은 [ADR-0003](decisions/0003-ADR-도메인과-영속모델-분리.md)에 있습니다.

### 배포 단위와 인스턴스

| 항목 | 내용 |
| :--- | :--- |
| **배포 단위** | 단일 애플리케이션입니다. 서비스 분리 운영 부담을 지지 않습니다 |
| **인스턴스 수** | 단일 인스턴스를 전제합니다 |

두 번째가 조용한 함정을 만듭니다. **단일 인스턴스를 전제하면 인메모리 상태가 허용되는데, 그 상태를 가진 채로 다중화하면 한도나 카운터가 인스턴스 수만큼 배수가 됩니다.** 오류 없이 값만 틀리므로 발견이 늦습니다. 인메모리 상태를 두는 자리는 공유 저장소 어댑터로 교체할 수 있는 형태로 만들고 그 사실을 11절에 등재합니다.

### 상위 층에서 내려오는 전제

| 전제 | 이 문서에 미치는 영향 | 원본 |
| :--- | :--- | :--- |

다섯 항목 모두 백엔드가 정한 것이 아니라 **받은 것**입니다. 바꾸려면 상위 문서를 먼저 고쳐야 합니다.

## 4. 아키텍처 전략

품질 목표(1절)와 제약 조건(2절)을 달성하기 위한 네 가지 전략입니다.

### 1) 배포 단위 — 모듈러 모놀리스

업무 도메인이 다양하더라도 서비스를 독립 배포 단위로 분리하지 않고, **단일 애플리케이션 안에서 모듈 경계를 명확히 나누는 구조**를 선택합니다.

- **선택 사유:** 팀 규모 대비 분산 트랜잭션 · 서비스 디스커버리 · 릴리스 관리의 부담을 지지 않습니다(목표 4). 모듈 간 호출이 동일 프로세스의 메서드 호출이므로 조회 조립 비용도 낮습니다.
- **트레이드오프:** 물리적 격리가 없으므로 타 모듈의 내부를 직접 참조하거나 타 테이블을 임의로 조인하는 오용이 가능합니다. **코드 수준의 강제가 없으면 이 구조는 성립하지 않습니다**(11절).

### 2) 도메인 분할 — 바운디드 컨텍스트

단일 거대 도메인 모델 대신 **업무 맥락에 따른 바운디드 컨텍스트**로 도메인을 분할합니다. 컨텍스트 간에는 공개 계약을 통해서만 통신합니다.

**경계를 새로 그을 때의 판정 기준은 애그리거트 소유입니다.** 어떤 유스케이스가 어느 컨텍스트에 속하는지는 그것이 **어느 애그리거트를 변경하는가**로 정합니다. 요구사항 묶음으로 나누면 같은 애그리거트를 두 컨텍스트가 변경하게 되어 트랜잭션 경계와 불변식의 소유자가 흐려집니다.

이미 그은 경계를 재검토할 때는 다른 세 질문을 씁니다. **용어가 다른가, 함께 변경되는가, 따로 살 수 있는가**입니다. 셋 다 아니면 경계를 잘못 그은 것이므로 합칩니다. 상세는 [컨텍스트 협력](concepts/컨텍스트-협력.md) 3절에 있습니다.

- **선택 사유:** 동일한 낱말이 용도에 따라 다른 의미를 갖는 복잡성을 경계로 흡수합니다. 판정 기준이 애그리거트 소유 하나로 고정되어 배치 결정에 재량이 들어가지 않습니다(목표 1).
- **트레이드오프:** 경계를 넘는 조회가 필요할 때마다 계약을 늘리거나 조인을 허용해야 합니다. 본 표준은 조회에 한해 조인을 허용하며 그 대가를 [ADR-0005](decisions/0005-ADR-컨텍스트-넘는-조인.md)에 기록했습니다.

### 3) 컨텍스트 내부 — 피쳐 절단

컨텍스트 내부의 1차 분류는 계층이 아니라 **피쳐**입니다. 컨트롤러 · 서비스 · DTO · 포트가 한 패키지에 모입니다.

- **선택 사유:** 요구사항 하나를 고칠 때 패키지 하나만 엽니다. 계층으로 나누면 같은 작업에 네 폴더를 오갑니다(목표 3).
- **트레이드오프:** 폴더명만으로 계층을 알 수 없습니다. 그래서 계층은 폴더 위치가 아니라 **클래스의 역할과 어노테이션으로 식별**하며, 그 식별을 사람이 아니라 ArchUnit이 합니다.

근거는 [ADR-0002](decisions/0002-ADR-피쳐-단위-패키지.md)입니다.

### 4) 데이터 접근 — 조회와 명령의 분리

별도 읽기 전용 저장소를 두는 완전한 CQRS 대신, **단일 데이터베이스 위에서 조회와 명령의 코드 경로만 분리**합니다.

| 경로 | 하는 일 | 접근 수단 |
| :--- | :--- | :--- |
| **명령** | 애그리거트를 로드해 불변식을 검증하며 상태를 바꿉니다 | 도메인 저장소 |
| **조회** | 화면이 요구하는 구조를 직접 만듭니다 | 피쳐가 소유한 조회 포트 |

- **선택 사유:** 조회를 도메인 모델에 태우면 **화면 요구가 도메인을 끌어당깁니다.** 목록에 표시명이 필요하다는 이유로 엔티티에 필드가 추가되고, 그 필드는 쓰기 로직에서 아무 의미가 없습니다(목표 2·3).
- **트레이드오프:** 같은 질문에 두 경로가 생깁니다. 명령 안의 중복 검사는 도메인 저장소로, 입력 중 실시간 안내는 조회 포트로 갑니다. 둘은 다른 이유로 진화하므로 나누는 것이 맞지만, 나눈 사실을 모르면 중복으로 보입니다.

**두 경로가 같은 도구를 씁니다.** 명령과 조회의 영속성 기술을 나누면 두 기술 사이의 flush 순서, 한쪽에서만 보이는 미커밋 변경, 조각 재사용 규칙 같은 항목이 규칙으로 자라납니다. 경로를 나누되 도구는 하나로 둡니다.

## 9. 아키텍처 결정 기록 (ADR)

주요 설계 선택의 사유와 기각한 대안은 `decisions/` 의 ADR로 관리합니다. 목록은 사이드바가 보여주므로 본 절에 다시 적지 않습니다.

### 대상 선정 기준

| 구분 | 기록 대상 (Do) | 비기록 대상 (Don't) |
| :--- | :--- | :--- |
| **대상 범위** | 구조 · 의존성 · 외부 인터페이스 · 주요 구현 기법에 영향을 주는 결정 ([Michael Nygard 기준](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)) | 단일 피쳐 내부의 일회성 구현 방식, 기존 패턴을 그대로 따르는 코드 추가 |
| **판단 기준** | 변경 비용이 높거나 설계 이유에 대한 설명이 반복적으로 필요한 항목 | 대안 검토 사실만 존재하는 단기성 결정 |

에이전트와의 협업 과정에서 생성되는 다수의 일시적 대안은 커밋 메시지로 기록하며 ADR로 발췌하지 않습니다.

### 채번 및 관리 규칙

- 파일명 포맷은 `XXXX-ADR-한글-슬러그.md`이며 스택 안에서 채번합니다.
- **결정 변경 시** 기존 ADR을 직접 수정하지 않고 신규 ADR을 작성해 이전 것을 상쇄하도록 기록합니다. 소규모 완화와 예외 추가는 원 ADR의 개정 절에 날짜와 함께 추기합니다.
- 커밋 메시지와 코드 주석이 ADR 번호를 참조하므로 부여된 번호는 변경하지 않습니다.
- 시스템이나 계약에 걸치는 결정은 여기가 아니라 상위 층의 `decisions/` 에 둡니다. **판정 기준은 프론트엔드가 그 결정을 알아야 하는가입니다.**

## 11. 리스크 및 기술 부채

### 품질 목표의 검증

| 품질 목표 | 검증 시나리오 | 판정 기준 |
| :--- | :--- | :--- |
| **부패 저항** | 타 컨텍스트의 내부 패키지를 참조하는 코드를 작성 | ArchUnit 실패로 빌드 차단 |
| **부패 저항** | 규칙 문서만 읽고 신규 코드의 배치 위치를 판정 | 문서 외 정보 없이 위치가 하나로 결정됨 |
| **도메인 독립성** | 도메인 패키지에서 프레임워크 타입을 임포트 | ArchUnit 실패로 빌드 차단 |
| **도메인 독립성** | 도메인 단위 테스트를 프레임워크 컨텍스트 없이 실행 | 순수 객체만으로 통과 |
| **변경 유연성** | 화면 요구 변경으로 응답 필드가 1개 추가 | 조회 포트와 DTO 수정만으로 완료. 도메인 변경 없음 |
| **운영 단순성** | 신규 기능 배포 | 단일 아티팩트 빌드와 배포로 완료 |

### 구조 규칙의 강제 수단

ArchUnit 규칙을 CI 게이트에 포함하며 **위반은 빌드 실패**입니다.

| 규칙 | 막는 것 |
| :--- | :--- |
| 타 컨텍스트는 `contract` 패키지만 참조 | 공개 계약을 거치지 않는 결합 |
| `domain`의 바깥 의존 금지 | 프레임워크가 도메인을 침식하는 것 |
| `application`의 `infrastructure` 의존 금지 | 기술이 유스케이스로 새는 것 |
| 피쳐 간 순환 금지 | 경계가 이름만 남는 것 |
| `shared`가 피쳐를 의존하지 않음 | 공유가 특정 피쳐에 묶이는 것 |
| 컨트롤러의 저장소 · 조회 포트 직접 의존 금지 | 서비스 층을 건너뛰는 지름길 |
| 명령 서비스의 조회 포트 의존 금지 | 명령이 도메인을 우회해 판단하는 것 |
| `common`이 어떤 컨텍스트도 의존하지 않음 | 바닥이 또 하나의 컨텍스트가 되는 것 |

| 대상 | 강제 수단 | 통제 방식 |
| :--- | :--- | :--- |
| **컨텍스트 경계와 의존 방향** | ArchUnit | 빌드 실패로 차단 |
| **코드 포맷** | Spotless | 빌드 실패로 차단 |
| **명명 규칙과 금지 패턴** | Checkstyle | 빌드 실패로 차단 |
| **버그 패턴** | SpotBugs | 빌드 실패로 차단 |
| **조인 허용 판정** | 없음 | **코드 리뷰 (수동)** |
| **애그리거트 간 ID 참조** | 없음 | **코드 리뷰 (수동)** |

구조를 바꿔야 하면 문서와 ADR을 먼저 고치고 ArchUnit 테스트를 함께 고칩니다. **테스트만 느슨하게 만드는 변경을 금지합니다.**

### 미검증 위험

| 항목 | 내용 | 완화 |
| :--- | :--- | :--- |
| **경계가 도구 하나에 의존** | Java 컴파일러가 패키지 경계를 강제하지 못해 컨텍스트 경계 전체가 ArchUnit 하나에 걸려 있습니다 | 규칙을 끄는 변경을 리뷰 대상으로 고정하고 완화가 필요하면 ADR로 남깁니다 |
| **읽기 경로의 스키마 결합** | 조회의 컨텍스트 간 조인을 허용했으므로 스키마 변경이 다른 컨텍스트의 조회를 깨뜨립니다. 코드상 참조가 없어 정적 분석으로 검출되지 않습니다 | 조회를 통합 테스트 필수 대상으로 두었습니다 |
| **피쳐 절단의 계층 불가시성** | 폴더명으로 계층을 알 수 없어 새로 합류한 사람이 클래스 역할을 오인할 수 있습니다 | 명명 규약을 고정하고 ArchUnit이 이름으로 판정하게 합니다 |
| **인메모리 상태와 다중화** | 시도 제한 카운터 등이 인스턴스마다 갈려 한도가 배수가 됩니다 | 다중화 시점에 공유 저장소 어댑터로 교체합니다 |
